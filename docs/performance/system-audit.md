# ผลตรวจการทำงาน KhunFlow

ตรวจวันที่ 10 ตุลาคม 2026 — ตรวจเว็บจริง โค้ด และทดสอบการบันทึกบนฐานข้อมูลแยก ไม่แก้ข้อมูลธุรกิจจริงและยังไม่แก้โค้ดแอป

## ขอบเขตและหลักฐาน

- เปิดตรวจ 20 เมนู: Dashboard, POS, สินค้า, สูตร, สต็อก, ตรวจนับ, ของเสีย, ซัพพลายเออร์, ใบสั่งซื้อ, รับของ, วันหมดอายุ, Variance, กำไร, รายงาน, คาดการณ์, ผู้ใช้, สิทธิ์, ธุรกิจ, กิจกรรม และผู้ดูแลแพลตฟอร์ม
- ตรวจ API เว็บจริง 21 เส้นทางด้วยบัญชีตัวอย่าง 4 บทบาท รวม 84 ครั้ง รายการอ่านที่อนุญาตของเจ้าของและผู้จัดการตอบสำเร็จ ไม่มี 500 ในชุดนี้
- ทดสอบบนฐานข้อมูลจำลอง 77 เงื่อนไข: ผ่าน 63 ไม่ผ่าน 14 เงื่อนไข หลายเงื่อนไขเป็นผลจากบัคเดียวกัน จึงไม่ใช่จำนวนบัค 14 จุด
- ทดสอบสร้าง/แก้ข้อมูล การตัดสต็อก ยกเลิกและคืนสถานะออเดอร์ รับของ ของเสีย ผู้ใช้ ร้าน สิทธิ์ และการรีเซ็ตรหัสผ่านตัวอย่าง การเปลี่ยนข้อมูลอยู่ในฐานจำลองและย้อนคืนหลังจบ
- Frontend build ผ่าน ตรวจ lint เฉพาะ src แล้ว; คำเตือน lint ไม่ได้ใช้เป็นหลักฐานว่าปุ่มเสีย
- หลักฐาน: `live-system-api.json`, `system-audit-tests.json`; ตัวทดสอบ `backend/tests/system_audit.py`

## จุดควรแก้ก่อน

| จุด | ผลที่พบ / วิธีทำซ้ำ | หลักฐาน | ความสำคัญ |
|---|---|---|---|
| กลับจากธุรกิจเดโม | เปิดข้อมูลตัวอย่าง → เปิดธุรกิจตัวอย่าง → กลับข้อมูลร้าน เก็บ business ID เป็น `demo` แล้ว API จริงแจ้ง “รหัสธุรกิจไม่ถูกต้อง”; ออกจากระบบแล้วเข้าใหม่จึงกลับมาใช้ได้ | เว็บจริง, AppLayout/หน้าธุรกิจ | สูง |
| หน้าตรวจนับหมุนค้าง | เมื่อ API ผิดพลาดจากกรณีข้างบน หน้าตรวจนับไม่จบ loading และไม่มีปุ่มลองใหม่; หน้า Expiration, Variance และ Profit มีรูปแบบจัดการข้อผิดพลาดเดียวกันในโค้ด แต่ไม่ได้บังคับให้ผิดพลาดบนเว็บทุกหน้า | เว็บจริงเฉพาะตรวจนับ + โค้ด | สูง |
| พนักงานเข้า Dashboard ไม่ได้ | บัญชีสต็อกเข้าสู่ระบบแล้วถูกพาไป Dashboard ซึ่ง API ไม่อนุญาต แสดงโหลดไม่สำเร็จ; API ของแคชเชียร์ถูกปฏิเสธเช่นกัน แต่เมนูและหน้าเริ่มต้นยังพามาที่นี่ | เว็บจริง + API 403 | สูง |
| ยืนยันใบสั่งซื้อกดแล้วเงียบ | ร้านไม่มีซัพพลายเออร์ เปิดออกใบสั่งซื้อใหม่แล้วกดยืนยัน: แบบฟอร์มค้าง ไม่มีข้อความว่าต้องเลือก/สร้างซัพพลายเออร์ โค้ดออกจากฟังก์ชันทันที | เว็บจริง, PurchasingPages.tsx | กลาง |
| รับของบางส่วนปิด PO ทั้งใบ | PO สองรายการ รับเพียง 1 จาก 10 ของรายการแรก สถานะเปลี่ยนเป็น received แล้วรับรายการที่เหลือไม่ได้ (409) | ฐานจำลอง | สูง |
| หน่วยในใบสั่งซื้อไม่ถูกส่ง | เลือกหน่วยในแบบฟอร์ม แต่ service ไม่ส่งหน่วยไป API; API ใช้หน่วยสต็อกแทน ทดสอบส่ง l กลับเป็น kg โดยไม่แจ้งเตือน | โค้ด + ฐานจำลอง | สูง |
| สูตรและของเสียต่างหน่วยบันทึกไม่ได้ | สต็อกเป็น kg แต่ใช้ 100 g ในสูตร/ของเสีย ถูกปฏิเสธ 422 แทนการแปลงหน่วยที่เข้ากันได้; ต้นทุนสูตรที่ควรได้ 2 ไม่เกิดขึ้น | ฐานจำลอง | สูง |
| รับของแล้วต้นทุนสินค้าเก่า | ต้นทุนเฉลี่ยวัตถุดิบเปลี่ยนหลังรับของ แต่ต้นทุนสูตร/สินค้าไม่คำนวณตาม ทดสอบได้ 2 แทน 2.1 ทำให้กำไรคลาดเคลื่อน | ฐานจำลอง | สูง |
| ปุ่มบันทึกสิทธิ์ไม่บังคับใช้ | หน้าสิทธิ์บันทึกเฉพาะ localStorage ไม่มีส่วนอื่นอ่านค่าและไม่มี API บันทึก แต่ข้อความระบุว่ามีผลทันที ไม่ได้กดเปลี่ยนสิทธิ์บัญชีจริง | โค้ด + ตรวจเส้นทาง API | สูง |

## ความถูกต้องของข้อมูลและหน้าจอเพิ่มเติม

1. **เปอร์เซ็นต์เปลี่ยนแปลง Dashboard เป็น 0 เสมอ:** โค้ดกำหนดไว้ตายตัวทั้งยอดขาย ต้นทุน และกำไร ทดสอบยอดขายวันนี้ 500 เมื่อวาน 100 ควรเปลี่ยน 400% แต่ตอบ 0
2. **กำไรจากต้นทุนที่ยังไม่พร้อม:** เว็บจริงหน้าสินค้าเตือนต้นทุน 0 แต่หน้ากำไรแสดงกำไร 100% จึงชวนให้เข้าใจว่าเป็นกำไรจริง ควรเตือนหรือแยกสินค้าที่ต้นทุนยังไม่ครบ
3. **รายงานเดโมเปลี่ยนช่วงแต่ข้อมูลเดิม:** กด 31 วันล่าสุด/31 วันก่อนหน้า ตารางเหมือนกัน เพราะ service เดโมไม่ใช้ offsetDays; โหมดข้อมูลร้านเปลี่ยนช่วงวันที่ได้
4. **บทบาทในรายชื่อผู้ใช้:** API แสดง User.role แทนบทบาทสมาชิกในร้านปัจจุบัน ทดสอบคนที่เป็น cashier ในร้านที่สองกลับแสดง owner ทั้งที่การตรวจสิทธิ์คำขอใช้บทบาทสมาชิกถูกต้อง
5. **สิทธิ์อ่านบาง API ไม่ตรงเมนู:** แคชเชียร์อ่าน waste/paged และ stock-counts ได้ (200) แม้เมนูไม่อนุญาต ควรกำหนดนโยบายให้ตรงกัน ไม่พบการอ่านข้อมูลข้ามร้านในชุดทดสอบ
6. **จัดการวันหมดอายุอยู่เฉพาะเครื่อง:** เช็คแล้ว/เอาออก ลบทิ้งถาวร และล้างประวัติ เก็บสถานะใน localStorage ไม่บันทึกที่ backend อีกเครื่องไม่เห็นสถานะ และคีย์ไม่แยกร้าน/บัญชี/เดโม การกดไม่ได้เปลี่ยนสต็อกหรือวันหมดอายุในฐานข้อมูล
7. **ตรวจนับรอบใหม่ใช้ยอดตั้งต้นเก่า:** โค้ดเปิดรอบใหม่โดยไม่โหลดสต็อกใหม่ จึงอาจแสดงผลต่างจากยอดก่อนรอบที่เพิ่งบันทึก ยังไม่ได้กดบันทึกจริงบนเว็บเพื่อทำซ้ำกรณีนี้
8. **สกุลเงิน/เขตเวลาที่ตั้งไม่ตรงการแสดงผล:** บันทึกสกุลเงินอื่นได้ แต่หน้าต่าง ๆ ยังแสดง ฿; ตัวจัดรูปแบบวันรายงานใช้ Asia/Bangkok คงที่
9. **Validation API ไม่ครบ:** Quantity ใบสั่งซื้อที่ไม่ใช่ตัวเลขทำให้ 500 แทน 422, สูตร items ว่างบันทึกได้และต้นทุนเป็น 0, timezone ที่ไม่มีจริงบันทึกได้ ชุดนี้ส่งข้อมูลผิดรูปแบบในฐานจำลอง ไม่ได้พบว่าฟอร์มปกติส่งค่าผิดรูปแบบเหล่านี้เอง

## หน้าไม่มีข้อมูลที่ยังไม่ถือเป็นบัค

บัญชีตัวอย่างที่ตรวจมีซัพพลายเออร์ ใบสั่งซื้อ และรับของเป็นศูนย์ จึงไม่มีรายการแสดง ส่วนออเดอร์ที่พบถูกยกเลิกแล้ว จึงไม่รวมในยอดขาย และข้อมูลคาดการณ์ไม่พอ การแสดงยอดขายศูนย์/คาดการณ์ว่างในกรณีนี้สอดคล้องกับข้อมูล ไม่ควรแก้ด้วยการใส่ยอดสมมติ

ปุ่มเปิดเมนู เปิด/ปิดฟอร์ม และเพิ่มสินค้าลงตะกร้าที่ตรวจทำงานได้ การบันทึกพื้นฐานหน่วยเดียวกัน การตัด/คืนสต็อก ยกเลิกและคืนสถานะออเดอร์ และการแยกข้อมูลร้านผ่านในชุดจำลอง ไม่มีการยืนยันรายการขายหรือปรับสต็อกจริงระหว่างการตรวจ

## ข้อจำกัด

ไม่ได้ยืนยัน OAuth Google จนจบ (ตรวจได้ว่าเริ่ม redirect ไป accounts.google.com), การส่งอีเมลจริง, หน้าต่างพิมพ์/ไฟล์ PDF, ทุกขนาดหน้าจอ และการเขียนสต็อกพร้อมกันจากหลายคน ไม่ได้กดทุกปุ่มบันทึกบนฐานจริง เพราะจะเปลี่ยนข้อมูลร้าน ผลนี้เป็นการตรวจครบเมนูหลักและกรณีที่ระบุ ไม่ใช่รับรองว่าไม่มีบัคอื่น

## ลำดับแนะนำ

แก้การกลับจากเดโม/หน้าเริ่มต้นตามบทบาท/ข้อผิดพลาดหมุนค้างก่อน จากนั้นรับของบางส่วน หน่วยและต้นทุน แล้วสิทธิ์ที่บันทึกไม่จริง ตามด้วย Dashboard และการแสดงกำไร ปัจจุบันรายงานนี้ยังไม่ได้แก้หรือ deploy การเปลี่ยนแปลงแอป
