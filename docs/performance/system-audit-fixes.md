# แก้ปัญหาจากการตรวจระบบ

วันที่ 10 ตุลาคม 2026

## สิ่งที่แก้

- กลับจากธุรกิจเดโมได้โดยไม่ส่ง business ID ของเดโมไป API จริง และกู้กรณี ID เดโมค้างจากเวอร์ชันเก่า
- หน้าเริ่มต้นของพนักงานคลังเป็นคลัง และแคชเชียร์เป็น POS; เมนูและเส้นทางอ่านสิทธิ์ของร้านปัจจุบัน
- ตรวจนับ วันหมดอายุ กำไร และ Variance จบสถานะโหลดเมื่อผิดพลาด มีข้อความและปุ่มลองใหม่; ป้องกันผลตอบกลับเก่าทับรายงานช่วงใหม่
- แบบฟอร์ม PO แสดงว่าต้องเพิ่มผู้ขายก่อน ปิดปุ่มเมื่อข้อมูลไม่พร้อม ป้องกันกดซ้ำ และส่งหน่วยจริง หน่วย kg/g และ l/ml แปลงจำนวนกับราคาต่อหน่วยเข้าหน่วยสต็อก; หน่วยที่แปลงกันไม่ได้ตอบ 422
- รับของบางส่วนไม่ปิด PO; ตรวจยอดรับสะสม ป้องกันรับเกินและรับซ้ำหลังครบ รองรับวัตถุดิบซ้ำในหลายบรรทัด แสดงยอดที่ยังรับไม่ครบในหน้ารับของ
- แก้ Enum หน่วยที่ทำให้สูตรและของเสียแปลงหน่วยไม่ได้; คำนวณต้นทุนสูตรและสินค้าใหม่จากต้นทุนเฉลี่ยหลังรับของ
- สิทธิ์บันทึกในฐานข้อมูลแยกตามร้านและมีผลที่ API ทุกคำขอ เจ้าของเปลี่ยนได้และลดสิทธิ์เจ้าของจนเข้าไม่ได้ไม่ได้ การยกเลิก/คืนสถานะออเดอร์ยังจำกัดเจ้าของและผู้จัดการ การเปลี่ยนบทบาท/ระงับบัญชียังคงข้อจำกัดเจ้าของเดิม
- API ของเสีย/ตรวจนับตรวจสิทธิ์ตรงกับหน้าจอ รายชื่อและรายละเอียดผู้ใช้แสดงบทบาทสมาชิกในร้านนั้น การแก้บทบาทร้านอื่นไม่เปลี่ยนบทบาทร้านหลัก
- วันหมดอายุบันทึกสถานะตรวจสอบ/ซ่อนที่ backend แยกร้าน ผูกกับวันหมดอายุปัจจุบัน เมื่อรับล็อตใหม่หรือแก้วันหมดอายุเปิดแจ้งเตือนใหม่ ปุ่มซ่อนคืนรายการได้และไม่ตัดสต็อก ต้องบันทึกของเสียหากทิ้งวัตถุดิบจริง
- เปอร์เซ็นต์ Dashboard คำนวณจากข้อมูลจริง เมื่อฐานวันก่อนเป็นศูนย์และวันปัจจุบันมีค่า จะไม่แสดงเปอร์เซ็นต์ที่คำนวณไม่ได้
- สินค้าต้นทุนศูนย์ไม่อยู่ในอันดับกำไร มีคำเตือนยอดกำไรรวมเป็นประมาณการ
- รายงานเดโมใช้ช่วงวันที่จริงและเติมวันไม่มีขายเป็นศูนย์ ช่วงก่อนหน้าไม่ซ้ำกับช่วงล่าสุด
- แสดงเงินตามสกุลเงินร้านและเวลาเหตุการณ์ตามเขตเวลาร้าน วันรายงานที่ API จัดกลุ่มตามร้านแล้วคงวันเดิม การเปลี่ยนสกุลเงินไม่แปลงตัวเลขย้อนหลัง
- ตรวจนับรอบใหม่โหลดสต็อกล่าสุด สูตรว่าง/PO จำนวนผิดรูปแบบ/ตัวเลขไม่จำกัด/เขตเวลาไม่มีจริงถูกปฏิเสธ แก้ปุ่มสั่งซื้อจากคาดการณ์ให้แสดงเหตุผลผิดพลาดและลองใหม่ได้
- จำกัด lint ที่ src เพื่อไม่สแกนไฟล์สร้างเสร็จและ dependencies

## ผลทดสอบ

- `system_audit.py`: **85/85 ผ่าน** รวมรับบางส่วน รับครบ รับเกิน รับซ้ำ และต้นทุนหลังรับของ
- `test_audit_regression.py`: **37/37 ผ่าน** ใช้การยืนยันตัวตนจริงบนฐานจำลอง รวมการเพิ่ม/ถอนสิทธิ์ ข้อมูลข้ามร้าน ข้อจำกัดยกเลิกออเดอร์ และวันหมดอายุล็อตใหม่
- `test_performance_regression.py`: **ผ่าน** การแบ่งหน้า ยอดรวม เขตเวลา สิทธิ์ การแยกร้าน คาดการณ์ สต็อก และ index ที่รันซ้ำได้ จำนวน query ของประวัติยังผ่านเพดานเดิม ไม่เพิ่มตามจำนวนรายการ
- Frontend build: **ผ่าน**; lint: ผ่านและยังมี warnings ที่ไม่ทำให้ build ล้ม
- ตรวจหน้าจอเว็บจำลอง: เปิด 18 เมนู ไม่พบข้อความผิดพลาดระหว่างตรวจ; เปิดธุรกิจเดโมแล้วกลับข้อมูลร้านสำเร็จ; รายงานเดโมสองช่วงต่างกัน; พนักงานคลังเข้า inventory และแคชเชียร์เข้า orders; เปลี่ยน USD บนธุรกิจจำลองแล้วหน้าคลังแสดง US$
- หยุด API จำลองแล้วเปิดตรวจนับ: แสดง 502 กับปุ่มลองใหม่ ไม่หมุนค้าง เมื่อเปิด API กลับ กดลองใหม่โหลดหน้าตรวจนับได้

การทดสอบเขียนข้อมูลใช้ฐาน `khunflow_perf_test` เท่านั้น ไม่ทำรายการขาย รับสินค้า หรือเปลี่ยนสิทธิ์ร้านจริงจากชุดทดสอบ

## การนำขึ้นใช้งานและข้อจำกัด

ตารางใหม่ `business_role_permissions` และ `ingredient_expiration_states` ถูกสร้างแบบเพิ่มผ่านขั้นตอนเริ่มระบบเดิม ไม่มีการรีเซ็ตฐาน ไม่มีการนำสิทธิ์ที่เคยอยู่เฉพาะ localStorage มาใช้กับฐานจริงโดยอัตโนมัติ ร้านเริ่มจากสิทธิ์มาตรฐานแล้วเจ้าของบันทึกใหม่ได้

รายการเก่าที่ปิดก่อนรับครบและมีประวัติรับของเชื่อมกับ PO มีปุ่ม “เปิดรับส่วนที่ยังไม่ครบ” สำหรับเจ้าของ/ผู้จัดการ API ตรวจยอดเดิมก่อนเปิดรับต่อ ไม่ตัดหรือเพิ่มสต็อกและไม่ปรับสถานะย้อนหลังอัตโนมัติ หากไม่มีประวัติรับที่เชื่อมกับ PO ต้องตรวจข้อมูลเดิมก่อน ไม่ได้ยืนยัน OAuth Google จนจบ การส่งอีเมลจริง การพิมพ์ PDF ทุกขนาดหน้าจอ หรือการเขียนสต็อกพร้อมกันจำนวนมาก

สถานะ deploy จะตรวจจาก revision ของ backend และไฟล์เว็บหลัง push ไม่ถือว่า build หรือ push สำเร็จเท่ากับ deploy สำเร็จ
