# โต๊ะและ QR สั่งอาหาร

## วิธีใช้

1. เข้าข้อมูลร้านจริง เลือกร้านที่ต้องการ แล้วเปิด **โต๊ะ & QR สั่งอาหาร**
2. เจ้าของร้านหรือผู้จัดการระบุจำนวนโต๊ะ/ที่นั่ง หรือเพิ่มชื่อโต๊ะเอง สูงสุด 200 โต๊ะต่อร้าน เพิ่มเป็นชุดได้ครั้งละ 100 โต๊ะ
3. ดาวน์โหลดภาพ QR ของแต่ละโต๊ะจากโดเมนที่ลูกค้าเข้าถึงได้ เช่น `https://khunflow.vercel.app` แล้วพิมพ์ติดโต๊ะ QR จาก localhost เปิดในโทรศัพท์เครื่องอื่นไม่ได้
4. ลูกค้าเปิด QR เลือกเมนู ใส่ตะกร้า/หมายเหตุ แล้วส่ง ไม่ต้องล็อกอินหรือสมัครบัญชี
5. พนักงานเปิด **คำสั่งซื้อ (POS)** คิวรอยืนยันอัปเดตทุก 10 วินาทีเมื่อหน้านั้นเปิดอยู่ กดโหลดใหม่ได้
6. กด **รับออเดอร์และตัดสต็อก** หรือปฏิเสธพร้อมเหตุผล ถ้าสต็อกไม่พอจะรับไม่ได้และรายการยังรอยืนยัน
7. ลูกค้าเปิดหน้าเดิมเพื่อติดตามสถานะ เก็บลิงก์ติดตาม 10 คำสั่งซื้อล่าสุดในเบราว์เซอร์นั้น ชำระเงินกับพนักงานที่ร้าน

ชื่อ/จำนวนที่นั่ง/เปิด–ปิดโต๊ะบันทึกในฐานข้อมูลแยกร้าน ปิดโต๊ะจะหยุดออเดอร์ใหม่แต่ไม่ลบคิวเดิม เปลี่ยน QR แล้วต้องพิมพ์ใหม่ ลิงก์เมนูเดิมใช้ไม่ได้ แต่ลิงก์ติดตามออเดอร์ที่ส่งแล้วใช้ต่อได้

เมนูแสดงสินค้าที่เปิดขายและราคามากกว่าศูนย์ ไม่รับประกันวัตถุดิบจนพนักงานยืนยัน หากราคาหรือสกุลเงินเปลี่ยนจากที่ลูกค้าตรวจไว้ ต้องโหลดเมนูและตรวจรายการใหม่ หากเปลี่ยนหลังส่งแล้วให้พนักงานปฏิเสธและให้ลูกค้าส่งใหม่

## สถานะและสต็อก

| การกระทำ | สถานะคำขอ | ยอดขาย/สต็อก |
|---|---|---|
| ลูกค้าส่ง | pending | ไม่เปลี่ยน |
| พนักงานรับ | accepted | สร้างออเดอร์ completed และหักตามสูตรใน transaction เดียว |
| พนักงานปฏิเสธ | rejected | ไม่เปลี่ยน |
| ยกเลิกออเดอร์ที่รับแล้ว | accepted + linked order cancelled | คืนสต็อกตาม snapshot เดิมและแสดงยกเลิกให้ลูกค้า |
| คืนสถานะออเดอร์ | accepted + linked order completed | ตรวจสต็อกและตัดตามกติกาเดิม |

ประวัติ POS แสดงชื่อโต๊ะ/หมายเหตุ การรับซ้ำล็อกคำขอแล้วคืนออเดอร์เดิม ไม่ตัดสต็อกซ้ำ สต็อกล็อกวัตถุดิบเรียงตาม ID และตรวจจำนวนก่อนเขียน การยกเลิกและคืนสถานะยังจำกัดเจ้าของ/ผู้จัดการ

## API

ทุกเส้นทางเริ่มด้วย `/api`:

| เส้นทาง | สิทธิ์/การใช้งาน |
|---|---|
| `GET /tables` | สิทธิ์ orders; โต๊ะและจำนวนคิวเฉพาะร้าน |
| `POST /tables` | เจ้าของ/ผู้จัดการ; `{name, seats}` |
| `POST /tables/batch` | เจ้าของ/ผู้จัดการ; `{count, seats}` |
| `PUT /tables/{id}` | เจ้าของ/ผู้จัดการ; `{name, seats, is_active}` |
| `POST /tables/{id}/rotate-qr` | เจ้าของ/ผู้จัดการ; ออก QR ใหม่ |
| `GET /table-orders` | สิทธิ์ orders; คิวรอยืนยันเฉพาะร้าน |
| `POST /table-orders/{id}/accept` | สิทธิ์ orders; รับรายการ |
| `POST /table-orders/{id}/reject` | สิทธิ์ orders; `{reason}` |
| `GET /public/tables/{token}/menu` | สาธารณะ; QR ระบุร้านและโต๊ะ |
| `POST /public/tables/{token}/orders` | สาธารณะ; ส่งรายการ |
| `GET /public/table-orders/{receipt}` | สาธารณะ; อ่านเฉพาะคำขอที่มี receipt ลับนี้ |

ตัวอย่างส่งออเดอร์:

```json
{
  "request_key": "c60ce894-badc-40c4-811d-57879aeabf94",
  "expected_currency": "THB",
  "items": [{"product_id": 1, "quantity": 2, "expected_price": 60}],
  "note": "ไม่ใส่น้ำตาล"
}
```

`expected_price` ใช้ตรวจว่าราคาเปลี่ยนหรือไม่ ยอดจริงใช้ราคาจากฐานข้อมูล `(table_id, request_key)` มี unique constraint ส่ง UUID เดิมจะได้คำขอเดิม ลูกค้าเลือก business ID สถานะยอดขาย หรือรับออเดอร์เองไม่ได้ API สาธารณะไม่ส่งต้นทุน สูตร สต็อก รายชื่อพนักงาน หรือออเดอร์ของลูกค้าคนอื่น

## การติดตั้งและขอบเขต

- Startup เดิมสร้างตารางใหม่ `dining_tables`, `table_order_requests` พร้อม constraints/index ของคิวและการจำกัดอัตราส่งผ่าน `metadata.create_all` ไม่รีเซ็ตหรือ seed ร้านจริง
- QR/receipt เป็น token สุ่ม 32 bytes ผู้ที่มีลิงก์ QR สั่งได้ จึงให้พนักงานตรวจโต๊ะก่อนรับ และเปลี่ยน QR ได้เมื่อลิงก์เผยแพร่นอกโต๊ะ
- จำกัด 50 เมนูไม่ซ้ำ/200 ชิ้นต่อคำขอ, 99 ชิ้นต่อเมนู, หมายเหตุ 500 ตัวอักษร, 30 คำขอต่อโต๊ะใน 5 นาที และคิวรอยืนยัน 100 คำขอต่อร้าน
- การจำกัดและคิวใช้ฐานข้อมูล ไม่ขึ้นกับตัวแปรใน process ของ Render
- หน้าลูกค้าแยกจากบัญชี/ร้านที่พนักงานล็อกอินอยู่ ใช้สกุลเงินจากร้านใน QR ไม่แปลงราคาตามอัตราแลกเปลี่ยน
- ล้างข้อมูลเว็บหรือเปลี่ยนเครื่องจะไม่ย้ายประวัติตามไป หากปิดการเก็บข้อมูลจะแสดงข้อความให้เปิดหน้าไว้
- รอบนี้ไม่มี payment gateway, แบ่งบิล, พิมพ์ครัวอัตโนมัติ หรือสถานะปรุง/เสิร์ฟ
- ตรวจ compilation/build และ API schema แล้ว ยังไม่ได้รันชุดทดสอบใหม่สำหรับ QR หรือทำรายการบนร้านจริง
